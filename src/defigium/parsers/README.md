# Parser Strategy: Redis

## 1. Introduction

This document details the implementation of the `IParser` strategy dedicated to interacting with the **Redis** in-memory database, specifically structured to process operational logs generated by the `MONITOR` command.

The `RedisParser` module acts as a domain adapter for the Redis ecosystem, fully fulfilling the responsibilities defined by the framework's interface:

1.  **Parsing (Ingestion):** Processes the raw log file generated by `MONITOR` and converts it into a continuous stream of Intermediate Event Format (IEF) objects.
2.  **Formatting (Exporting):** Performs the inverse operation, translating synthetic IEF events back into the native `MONITOR` syntax, ensuring read compatibility for the Executor Module.
3.  **Synthetic Argument Generation:** Provides the stochastic logic required to synthesize realistic arguments (e.g., arbitrary payloads) for state-mutating operations, such as `HMSET` and `SET`.

## 2. Implementation and Features

### 2.1. Ingestion and Parsing (Log to IEF)

The `RedisParser` architecture was designed to handle the syntactic idiosyncrasies of the `MONITOR` command.

* **Regular Expression Extraction:** An initial routine (`_LOG_LINE_REGEX`) segments each record into three fundamental components: the timestamp, the source identifier (`[client_id]`), and the operational instruction (command string).
* **Custom Argument Parsing:** Due to the permissiveness of the Redis protocol—which allows whitespaces within quote-delimited literals—the parser employs a custom analyzer (`_parse_command_args`). This component segments the instruction while respecting literal boundaries and preserving the integrity of raw strings.
* **Structural Mapping:**
    * `op_type`: Extracted directly from the first token of the instruction (e.g., "HMSET").
    * `target`: Determined by the second token, representing the access key (e.g., "user:123").
    * `additional_data['raw_args']`: A list structure that encapsulates all subsequent parameters (e.g., fields and values of a hash).
* **Temporal Granularity:** The extracted timestamps are normalized and rounded according to the precision defined in the `config.yaml` file (e.g., five decimal places).
* **Semantic Mapping:** To enable domain-agnostic statistical modeling, the parser abstracts native Redis commands into universal semantic categories (`CREATE`, `READ`, `UPDATE`, `DELETE`).

### 2.2. Formatting (IEF to Log)

The formatting routine (`format`) operates in the final synthesis stage, reconstructing instructions in the `MONITOR` standard from synthetic IEF events. The process ensures that semantic components (`op_type`, `target`, and `raw_args`) are validly concatenated, properly enclosed in double quotes, and separated by spaces.

### 2.3. Argument Synthesis

The `generate_args` method is dynamically invoked by generative strategies (such as the `HeatmapGenerator`) during the instantiation of non-deterministic operations. The `RedisParser` encapsulates the logic to formulate credible synthetic data payloads:

* **HMSET:** Synthesizes a random cardinality of field-value pairs populated with arbitrary data.
* **SET:** Generates a random string to act as a scalar value.
* **ZADD:** Computes a floating-point numeric `score` and selects a pseudo-random `member` from the previously mapped key space.

### 2.4. Supported Commands Scope

To ensure analytical precision within the context of the experimental evaluation (e.g., execution of the YCSB Workload A), this implementation focuses on a specific subset of commands.

Operations with full parsing and semantic mapping support include:
* `HMSET`
* `HGETALL`
* `ZADD`

Connection management and infrastructure instructions (e.g., `CLIENT`) are considered semantically irrelevant for primary workload modeling and are thus summarily filtered during the ingestion phase.

## 3. Dependencies

The `RedisParser` implementation is structurally self-sufficient and introduces no external dependencies (e.g., `pip` packages). The entire parsing infrastructure relies natively on the Python standard library.

## 4. Configuration

Activating this parsing module requires setting the following directive in the central `config.yaml` orchestration file:

```yaml
parser:
  type: redis
```
